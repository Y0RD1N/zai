# Zai integra su propio motor multiproveedor

**La mejor opción para Zai es construir un motor propio, integrado en el instalador y presentado como «Zai Agent», con adaptadores para DeepSeek, OpenRouter, Ollama Cloud, Ollama local y servicios compatibles.** El motor puede compartir las ventanas, aprobaciones y conexiones al navegador que ya existen para Codex y Claude. Electron incorpora Node, de modo que el usuario no necesita instalar un CLI adicional para ejecutar este coordinador. Pi ofrece una alternativa embebible y OpenCode aporta más funciones preparadas, pero ambos introducen un núcleo externo que Zai tendría que adaptar, actualizar y reconocer. Ninguna de estas rutas proporciona automáticamente todas las funciones de Claude Code ni la misma fiabilidad con cualquier modelo. La recomendación respeta la preferencia de escribir el código de Zai: implementar su bucle, herramientas y políticas, sin copiar otro proyecto, y certificar progresivamente las capacidades de cada modelo. **Este informe distingue arquitectura propuesta de funciones ya existentes; no certifica que todo lo descrito esté implementado.** Investigación documental verificada el 16 de octubre de 2026; no se realizaron inferencias de pago ni se consultaron credenciales personales. ([Procesos de Electron](https://www.electronjs.org/docs/latest/tutorial/process-model), [Pi SDK](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/sdk.md), [Servidor OpenCode](https://opencode.ai/docs/server/))

## Un motor propio conserva el control de la pizarra

El harness es el programa que mantiene la conversación, pide una respuesta al modelo, interpreta sus llamadas a herramientas, consulta permisos, ejecuta operaciones y devuelve resultados hasta completar la tarea. El modelo aporta decisiones y texto; **Zai conserva la autoridad para leer archivos, lanzar procesos o actuar en el navegador**. La ventana gráfica debe representar al agente y su sesión, mientras el proveedor y el modelo se seleccionan dentro de ella. Así se puede cambiar de DeepSeek a un modelo local sin convertir la ventana en una imitación de Claude. El código actual ya separa adaptadores de agentes y eventos de mensajes, herramientas y aprobaciones, y dispone de un broker de navegador; constituye una base aprovechable para este diseño. ([Gestor actual de Zai](/home/yordi/Documentos/projects/zai/electron/agents.cjs), [Broker actual de Zai](/home/yordi/Documentos/projects/zai/electron/browser-hub.cjs))

| Alternativa | Qué aporta | Trabajo que sigue correspondiendo a Zai | Decisión |
| --- | --- | --- | --- |
| Motor propio | Control del bucle, protocolos, herramientas, historial y experiencia gráfica | Implementar y probar todo el coordinador, además de mantenimiento de proveedores | **Recomendado** para un harness original y coherente con la pizarra |
| Pi embebido | SDK de sesiones, eventos, herramientas, compacción y recursos | Permisos, aislamiento, navegador, adaptación de extensiones y funciones avanzadas | Alternativa si se acepta un núcleo de agente como dependencia |
| OpenCode empaquetado | Motor con servidor, sesiones, agentes, permisos, skills, MCP y plugins | Distribuir el ejecutable correcto, administrar proceso/autenticación y traducir eventos a la UI | Motor opcional si prima disponer antes de más funciones |

Pi está actualmente en `earendil-works/pi`; el paquete consultado es `@earendil-works/pi-coding-agent` 1.3.0, con Node 22.19 o posterior. Permite sustituir herramientas y almacenamiento, pero **no incorpora un sistema de permisos o sandbox**, y deja subagentes y planificación fuera de su núcleo predeterminado. Su integración MCP en el SDK también necesita configuración explícita. Esta composición resulta útil, pero no elimina el trabajo más importante de Zai: decidir qué puede hacer cada agente. ([Pi SDK](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/sdk.md), [Seguridad de Pi](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/security.md), [Alcance de Pi](https://github.com/earendil-works/pi))

OpenCode expone un servidor HTTP con eventos SSE y SDK TypeScript. Tiene agentes principales y subagentes, descubrimiento de skills y permisos configurables. Sin embargo, instalar `@opencode-ai/sdk` no instala por sí solo el motor: su lanzador ejecuta `opencode` desde PATH. Una distribución controlada por Zai tendría que incluir un binario fijado por sistema y arquitectura, iniciarlo desde una ruta absoluta y proteger el servidor local con credenciales efímeras. No se ejecutaron benchmarks que permitan atribuir mejor calidad de programación a Pi u OpenCode con el mismo modelo. ([Servidor y autenticación](https://opencode.ai/docs/server/), [Agentes](https://opencode.ai/docs/agents/), [Lanzador SDK 1.19.3](https://github.com/anomalyco/opencode/blob/v1.19.3/packages/sdk/js/src/server.ts))

## Cuatro proveedores requieren adaptadores con capacidades reales

Compartir un formato parecido a OpenAI simplifica el transporte, pero no vuelve idénticos los proveedores. Conviene mantener un contrato interno para consultar modelos, transmitir respuestas, conservar mensajes originales, normalizar uso y cancelar operaciones. Para DeepSeek y OpenRouter puede compartirse parte del parser SSE; para Ollama recomiendo su API nativa NDJSON, que expone contexto y metadatos adicionales. Los identificadores y capacidades deben consultarse al conectar, evitando fijar permanentemente nombres de modelos. ([DeepSeek Models](https://api-docs.deepseek.com/api/list-models/), [OpenRouter Models](https://openrouter.ai/docs/guides/overview/models), [Ollama streaming](https://docs.ollama.com/api/streaming))

| Proveedor | Conexión recomendada | Autenticación y descubrimiento |
| --- | --- | --- |
| DeepSeek | Base `https://api.deepseek.com`, `POST /chat/completions` | Bearer; `GET /models` para modelos, contexto y capacidades publicadas |
| OpenRouter | Base `https://openrouter.ai/api/v1`, `POST /chat/completions` | Bearer; `GET /models`, modalidades y parámetros admitidos |
| Ollama Cloud | Base `https://ollama.com/api`, `POST /chat` | Bearer; `GET /tags`; acceso directo sin instalar Ollama |
| Ollama local | Base `http://localhost:11434/api`, `POST /chat` | Normalmente sin clave; `/tags`, `/show` y `/ps` para modelos y capacidades |
| Otro servicio compatible | URL y modelo configurados por el usuario | Perfil independiente; comprobar herramientas, streaming y formato de errores |

Los endpoints de la tabla proceden de sus contratos oficiales. El acceso local a Ollama también puede utilizar modelos remotos: un servidor en `localhost` no demuestra por sí mismo que el cómputo sea local. Zai debe señalar el destino real y distinguir el máximo de contexto del modelo del contexto efectivamente cargado en la máquina. ([DeepSeek](https://api-docs.deepseek.com/), [OpenRouter](https://openrouter.ai/docs/api_reference/overview), [Ollama Cloud](https://docs.ollama.com/cloud), [Ollama API](https://docs.ollama.com/api/introduction), [Contexto de Ollama](https://docs.ollama.com/context-length))

**Preservar el protocolo original es indispensable para agentes de varios pasos.** DeepSeek exige conservar `reasoning_content` de los turnos anteriores cuando se usan herramientas; OpenRouter puede devolver `reasoning_details` con firmas o datos cifrados que deben mantenerse en orden. Ollama nativo devuelve argumentos de herramientas como objetos y combina fragmentos de pensamiento, texto y llamadas. Reducir todo el historial a texto visible rompe estas secuencias. El motor necesita acumular fragmentos completos, validar el JSON contra un registro cerrado de herramientas, ejecutar después del permiso y devolver los resultados usando los identificadores y campos correctos. ([Thinking de DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode/), [Razonamiento de OpenRouter](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens), [Herramientas de Ollama](https://docs.ollama.com/capabilities/tool-calling))

La interfaz debe mostrar esfuerzo, visión y herramientas solo cuando el modelo y el endpoint los admitan. Un modelo sin herramientas puede utilizarse para conversar; no debe anunciarse como agente autónomo completo. Tampoco existe una velocidad «Rápida» universal equivalente a la de Codex: pueden mostrarse opciones de rendimiento documentadas y tokens por segundo medidos. La compatibilidad HTTP requiere pruebas funcionales, especialmente en modelos locales pequeños. ([Parámetros y routing de OpenRouter](https://openrouter.ai/docs/guides/routing/provider-selection), [Thinking de Ollama](https://docs.ollama.com/capabilities/thinking), [Métricas de Ollama](https://docs.ollama.com/api/usage))

Los indicadores económicos deben conservar su significado. DeepSeek publica saldo; OpenRouter publica uso y límites de clave; Ollama Cloud publica saldo incluido y comprado, y determinadas cuentas anteriores mantienen ventanas de sesión o semana. Ollama local ofrece tokens y tiempos, sin cuota de suscripción. **No convertir saldo en un porcentaje semanal ni inventar una ventana de cinco horas.** Los costes calculados se etiquetan como estimaciones; los publicados por el proveedor conservan su origen y fecha. Detener una petición remota tampoco garantiza coste cero ni cancelación inmediata de la facturación. ([Saldo DeepSeek](https://api-docs.deepseek.com/api/get-user-balance/), [Límites OpenRouter](https://openrouter.ai/docs/api_reference/limits), [Contabilidad OpenRouter](https://openrouter.ai/docs/cookbook/administration/usage-accounting), [Saldo Ollama](https://docs.ollama.com/api/balance), [Cancelación de streaming](https://openrouter.ai/docs/api_reference/streaming))

## El navegador y las skills necesitan una política común

El diseño recomendado separa un host de agentes, adaptadores de proveedor, broker de herramientas, registro de skills y almacén de sesiones. Cada sesión conserva mensajes originales, llamadas y resultados, decisiones de aprobación y cambios de configuración; la pizarra guarda sus posiciones y referencias. El motor impone límites de pasos, tiempo y tamaño de salida, y puede detener HTTP y procesos propios. Electron permite aislar el coordinador en un `utilityProcess`, aunque ese proceso **no constituye por sí mismo un sandbox del sistema operativo**. La elección de procesos y políticas es propuesta de ingeniería, no una capacidad que aparezca al elegir un modelo. ([Electron utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process), [Sesiones Pi](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/sessions.md), [Permisos Claude](https://code.claude.com/docs/en/permissions))

El navegador conectado utiliza el broker existente de Zai. El motor propio puede invocar sus herramientas sin necesitar un «servidor de navegador» particular de DeepSeek u Ollama. Las instantáneas semánticas y referencias permiten operar con modelos de texto; interpretar capturas requiere visión. **El cable representa acceso real y revocable**, con comprobación del proyecto, agente y navegador antes de cada acción. La animación debe corresponder a una operación ejecutada, no a que el modelo esté escribiendo o razonando. ([Broker de Zai](/home/yordi/Documentos/projects/zai/electron/browser-hub.cjs), [Controlador de Zai](/home/yordi/Documentos/projects/zai/electron/browser-controller.cjs), [Contrato de herramientas Ollama](https://docs.ollama.com/capabilities/tool-calling))

Para permitir desconectar con seguridad, propongo un control visible en el punto conectado o en el pie del navegador, además de seleccionar el cable. Se puede desconectar mientras el agente trabaja en archivos o conversa. Durante una acción de navegador activa, la UI muestra «Navegador ocupado» y el proceso principal rechaza la retirada de ese enlace. La comprobación debe ser atómica respecto a la cola de herramientas: **una animación apagada en la UI no prueba que el navegador esté libre**. Al retirar el cable se invalidan el acceso y las aprobaciones pendientes de esa conexión, y las llamadas que aún no comenzaron vuelven a comprobar autorización. Cerrar o detener explícitamente un agente necesita una vía separada para cancelar su trabajo. Este comportamiento es una recomendación para corregir la gestión actual, no una prueba de implementación realizada por esta investigación. ([Punto de integración actual](/home/yordi/Documentos/projects/zai/electron/browser-hub.cjs))

Las skills requieren un índice de nombres y descripciones y la carga de `SKILL.md` cuando corresponda, mostrando origen y requisitos. Es razonable reconocer directorios de Zai y `.agents/skills`, y evaluar compatibilidad con `.claude/skills`. Leer una skill no debe ejecutar automáticamente sus scripts, hooks o extensiones. Los formatos de instrucciones pueden compartirse, pero campos específicos, herramientas ausentes o permisos diferentes impiden prometer portabilidad total. ([Skills OpenCode](https://opencode.ai/docs/skills/), [Mecanismos de extensión Claude](https://code.claude.com/docs/en/features-overview))

| Familia de funciones | Base actual de Zai | Alcance que necesita el motor propio |
| --- | --- | --- |
| Chat, streaming y estado | Ventanas Codex/Claude y eventos gráficos | Adaptadores multiproveedor y bucle original, con llamadas/resultados en orden |
| Archivos, búsqueda y terminal | Proyectos, carpetas y terminal de la pizarra | Herramientas acotadas, escrituras atómicas, aprobación y cancelación |
| Navegador y cable | Broker, acciones y actividad existentes | Registrar el tercer agente, aplicar permisos y proteger desconexiones ocupadas |
| Modelos, esfuerzo y uso | Controles de agentes nativos | Catálogos y métricas específicas por proveedor, sin capacidades supuestas |
| Skills y memoria de proyecto | Capacidades de los motores nativos | Descubrimiento y carga propios; política explícita para instrucciones y recursos |
| Sesiones y compacción | Conversación y estado persistidos | Historial de protocolo reanudable y resumen que conserve el registro original |
| Planificación y subagentes | Funciones disponibles según motor nativo | Scheduler, contextos separados, permisos reducidos y cancelación heredada |
| MCP, hooks, comandos y plugins | MCP propio del navegador | Clientes/configuración y contratos de extensión propios; confianza explícita |
| Checkpoints y revisión | Dependen del motor nativo | Captura de archivos modificados, diff y restauración que detecte cambios posteriores |
| Sandbox y servicios exclusivos | Dependen del CLI y del sistema | Aislamiento por SO como trabajo adicional; los servicios alojados no se trasladan |

Esta matriz organiza el trabajo y **no acredita paridad entregada con Claude Code**. Su documentación distingue skills, memoria, MCP, hooks, plugins y subagentes; no basta con un bucle de chat para obtenerlos. Los checkpoints tampoco equivalen a una copia íntegra del proyecto, ni siquiera en Claude: tienen límites frente a comandos de shell y cambios externos. Un modo solo lectura debe bloquear shell mutante y herramientas MCP que escriben, además de las herramientas de archivos. Un `cwd` o una instrucción al modelo no impiden que un proceso acceda a otras rutas. ([Funciones Claude](https://code.claude.com/docs/en/features-overview), [Subagentes](https://code.claude.com/docs/en/sub-agents), [Hooks](https://code.claude.com/docs/en/hooks), [Checkpoints](https://code.claude.com/docs/en/checkpointing), [Permisos](https://code.claude.com/docs/en/permissions))

## El instalador puede incluir el harness sin incluir los modelos

Un motor original escrito para el Node integrado de Electron se distribuye con Zai en Windows, Fedora y macOS. No exige que el usuario ejecute `npm install -g` ni que configure un nuevo CLI. Deben verificarse empaquetado, rutas, shell disponible, cancelación de procesos y módulos nativos en cada sistema. **Instalar el harness no instala Ollama, un generador de imágenes ni sus pesos**: Ollama Cloud funciona directamente por API, mientras la inferencia local necesita un servicio y modelos adecuados al hardware. Es preferible detectar servicios locales y explicar sus requisitos antes de descargar varios gigabytes. ([Electron](https://www.electronjs.org/docs/latest/tutorial/process-model), [Ollama Cloud](https://docs.ollama.com/cloud))

Pi y OpenCode publican licencia MIT; la versión actual consultada de Vercel AI SDK publica Apache-2.0. Usarlos como dependencias requiere conservar sus avisos y revisar los artefactos concretos, sin atribuir su código a Zai. Claude Agent SDK está sujeto a sus términos comerciales y no debe tratarse como un motor libre genérico para todos los proveedores. Esta investigación identifica licencias principales, pero no sustituye la revisión de dependencias transitivas ni de condiciones de redistribución de cada binario. ([Licencia Pi](https://github.com/earendil-works/pi/blob/main/LICENSE), [Licencia OpenCode](https://github.com/anomalyco/opencode/blob/dev/LICENSE), [Licencia AI SDK](https://github.com/vercel/ai/blob/main/LICENSE), [Términos Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview))

Las claves pertenecen al proceso principal y a un archivo privado separado del workspace. `safeStorage` utiliza Keychain, DPAPI o almacenes de secretos de Linux; en Linux puede seleccionar `basic_text`, que no ofrece protección adecuada. En ese caso recomiendo **guardar claves solo en memoria durante la sesión**, hasta disponer de un almacén seguro. La interfaz recibe únicamente identificadores y estado «configurada», no una lectura posterior del secreto. Exportaciones de pizarra, terminales, prompts y registros deben excluir las credenciales; su presencia en el instalador nunca es necesaria. ([Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage), [Seguridad Electron](https://www.electronjs.org/docs/latest/tutorial/security))

Cada clave queda vinculada al origen configurado. Los perfiles cloud incorporados fijan HTTPS y hosts conocidos; Ollama local admite el destino local explícito, y un servidor LAN o compatible se configura como perfil aparte. Cambiar la URL no debe reenviar automáticamente una clave de otro proveedor. Las solicitudes se realizan desde main, validando el emisor IPC y evitando redirecciones que trasladen autenticación a otro host. Estas medidas también impiden que una página del navegador conectado reconfigure proveedores o consulte el almacén de secretos. ([Seguridad Electron](https://www.electronjs.org/docs/latest/tutorial/security), [Autenticación Ollama](https://docs.ollama.com/api/authentication), [Prevención SSRF de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html))

## Los fondos se integran como imágenes independientes del chat

La personalización puede ofrecer color sólido, imagen importada y generación mediante un proveedor de imágenes. El fondo debe ocupar una capa propia bajo las ventanas, con ajuste de encuadre e intensidad; oscurecer o desenfocar esa capa no debe afectar al texto ni a los iconos. Para importar una imagen, Zai puede decodificar PNG/JPEG/WebP, limitar tamaño y dimensiones, copiarla a su biblioteca local y guardar un identificador. Un protocolo de activos restringido sirve ese archivo sin exponer rutas arbitrarias. Esta estructura evita depender de la ubicación original de la foto y evita introducir base64 enorme en cada guardado del tablero. ([Electron nativeImage](https://www.electronjs.org/docs/latest/api/native-image), [Protocolos Electron](https://www.electronjs.org/docs/latest/api/protocol))

Para nube recomiendo adaptadores diferenciados. OpenAI utiliza `POST /v1/images/generations`; OpenRouter ya publica su propio `POST /api/v1/images` y catálogo `GET /api/v1/images/models`. No conviene suponer que cualquier endpoint de chat genera imágenes. El modelo, formato y proporción deben elegirse según capacidades consultadas; una clave DeepSeek de chat no se convierte por ello en una clave de generación visual. La aplicación debe solicitar una generación solo tras una acción explícita y presentar sus errores o costes reales. No se verificó acceso autenticado a los modelos de ninguna cuenta. ([API OpenAI](https://developers.openai.com/api/reference/resources/images/methods/generate), [Imágenes OpenRouter](https://openrouter.ai/docs/guides/overview/multimodal/image-generation), [Catálogo de imágenes](https://openrouter.ai/docs/api/api-reference/images/list-image-models))

Para ejecución local, **AUTOMATIC1111/Forge ofrece el adaptador inicial más sencillo**, mediante `/sdapi/v1/txt2img` y respuesta base64. ComfyUI aporta workflows y cola por identificador, con `/prompt`, eventos y recuperación de resultados; exige comprobar que los modelos y nodos del workflow existan. Un workflow importado no autoriza descargar ni ejecutar nodos personalizados. ComfyUI publica GPL-3.0 y AUTOMATIC1111 AGPL-3.0: conectar sus APIs como servicios separados evita convertir una integración pequeña en un instalador de Python, GPU y pesos, cuyas licencias también deben revisarse. ([API A1111](https://github.com/AUTOMATIC1111/stable-diffusion-webui/wiki/API), [API Forge](https://github.com/lllyasviel/stable-diffusion-webui-forge/blob/main/modules/api/api.py), [Rutas ComfyUI](https://docs.comfy.org/development/comfyui-server/comms_routes), [Licencia ComfyUI](https://github.com/Comfy-Org/ComfyUI/blob/master/LICENSE), [Licencia A1111](https://github.com/AUTOMATIC1111/stable-diffusion-webui/blob/master/LICENSE.txt))

La documentación consultada de Ollama presenta generación de imágenes experimental anunciada para macOS, con Linux y Windows todavía indicados como próximos; además, una rama de documentación experimental difiere del código principal recuperado. **No hay evidencia suficiente en esta investigación para prometer imágenes locales mediante Ollama en Fedora o Windows.** El chat y la visión de Ollama no prueban esa capacidad de generación. Zai puede reservar un adaptador experimental, condicionado a versión y detección funcional, mientras usa A1111/Forge o ComfyUI para el caso local verificable. ([Anuncio Ollama](https://ollama.com/blog/image-generation), [Rama experimental](https://github.com/ollama/ollama/blob/ollama-imagegen-docs/docs/api.md#image-generation-experimental), [Tipos de main](https://github.com/ollama/ollama/blob/main/api/types.go))

El progreso debe reflejar eventos del motor. En A1111 el progreso y la interrupción afectan estado compartido, por lo que cancelar desde Zai no debe interrumpir silenciosamente una tarea de otra aplicación. En ComfyUI hay que filtrar por `prompt_id` y mostrar pasos o fases, sin convertir el avance de un nodo en porcentaje global ficticio. Si una API no ofrece progreso, basta un estado indeterminado y cancelación de espera. Las imágenes recibidas por URL se descargan con límites y sin enviar la clave del proveedor al CDN. ([Estado compartido A1111](https://github.com/AUTOMATIC1111/stable-diffusion-webui/blob/master/modules/api/api.py), [Eventos ComfyUI](https://docs.comfy.org/development/comfyui-server/comms_messages))

## Conclusión

La unidad que conviene certificar es la combinación **Zai + proveedor + modelo + conjunto de herramientas**. Un primer alcance útil comprende chat en streaming, archivos y búsqueda, terminal con aprobación, navegador conectado, skills, sesiones y detención. La compacción, subagentes, hooks, plugins, MCP adicional y checkpoints deben incorporarse como capacidades verificadas por separado. La aceptación necesita pruebas de fragmentación de streaming, razonamiento conservado, permisos denegados, rutas y symlinks, cancelación concurrente, reanudación y desconexión durante operaciones; una demostración visual no valida esos límites.

Este enfoque convierte la pizarra en la superficie común de trabajo y mantiene reemplazable el modelo. También permite que una instalación sin GPU use APIs, y que otra instalación use servicios locales, sin duplicar toda la aplicación. El criterio de avance es concreto: cada función anunciada debe corresponder a una herramienta, una política y una prueba; la etiqueta «compatible con Claude Code» por sí sola no aporta ninguna de esas garantías.
